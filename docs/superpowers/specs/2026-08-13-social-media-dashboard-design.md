# Веб-дашборд аналитики соцсетей для агентства — дизайн

Дата: 2026-08-13

## 1. Цель и контекст

Внутренний инструмент агентства для мониторинга страниц в соцсетях —
своих аккаунтов, аккаунтов клиентов и (в ограниченном виде) чужих
публичных аккаунтов. Поддерживаемые платформы: Telegram, Instagram,
VK, YouTube, LinkedIn.

Пользователи: только сотрудники агентства (единая роль, без
клиентского доступа). Ожидаемый масштаб: небольшое агентство,
10–30 отслеживаемых аккаунтов.

### Ключевые сценарии
- Обзор нескольких выбранных аккаунтов сразу (карточки по платформам).
- Детальная страница одного аккаунта (свой или клиентский) — сводная
  статистика + список/топ постов с фильтром по типу поста.
- Страница сравнения нескольких аккаунтов — таблица метрик и
  наложенные графики трендов за период.
- Ручное и плановое обновление данных.

### Ограничение по данным (важно для архитектуры)
Официальные API платформ используются напрямую. Для аккаунтов, к
которым агентство имеет доступ как администратор/партнёр (свои +
клиентские, подключённые через Meta Business Suite, VK-токен
сообщества, YouTube Studio, LinkedIn Marketing API, Telegram
Bot/MTProto), доступна полная статистика: охваты, показы, ER,
демография.

Для чужих публичных аккаунтов без выданного доступа (например,
конкуренты) — данные по Instagram и LinkedIn ограничены тем, что
официально видно на публичной странице (подписчики, число постов,
лайки/комментарии под постами, где это публично). Охваты, показы и
демография для таких аккаунтов недоступны в принципе — это
осознанное ограничение, не техдолг. Самостоятельный скрапинг
исключён (нарушение ToS, юридический риск, нестабильность). VK,
YouTube и Telegram отдают публичную статистику по открытым методам
API даже без прав администратора.

## 2. Технологический стек

- **Backend:** Node.js + TypeScript, NestJS (модульность из коробки
  хорошо ложится на архитектуру "по коннектору на платформу").
- **Frontend:** React + TypeScript (Vite или Next.js в режиме SPA).
- **БД:** PostgreSQL.
- **Очередь задач:** BullMQ (Redis) — для планового и ручного сбора
  данных.
- **Деплой:** Docker Compose (backend, frontend, Postgres, Redis) на
  одном VPS/сервере агентства. Подходит по масштабу, просто в
  эксплуатации, не требует облачного вендора.

### Компоненты backend
- **API-слой** — CRUD по отслеживаемым аккаунтам; эндпоинты обзора,
  детальной статистики, сравнения; эндпоинт "обновить сейчас";
  эндпоинт статуса job.
- **Коннекторы** — модуль на платформу, единый интерфейс:
  `getAccountInfo()`, `getAccountStats(period)`, `getPosts(period)`.
  Инкапсулирует токены, специфику API и rate-limit конкретной
  платформы. Для аккаунтов без выданного доступа коннектор работает в
  ограниченном режиме (только публично видимые поля, см. раздел 1).
- **Scheduler / job runner (BullMQ)** — ежедневный автозапуск сбора по
  всем активным аккаунтам; ручные job'ы от кнопки "обновить сейчас" —
  с более высоким приоритетом в очереди; последовательная обработка
  job'ов одной платформы с паузой под её rate-limit.
- **Auth** — email/пароль, единая роль для всех сотрудников, сессия по
  JWT.

### Frontend — страницы
1. **Обзор** выбранных аккаунтов — карточки по всем платформам с
   ключевыми метриками.
2. **Детальная статистика** одного аккаунта (свой/клиентский) —
   сводка (подписчики, лайки, комментарии, просмотры, охват, ER) +
   список постов за период + топ постов + фильтр по типу поста
   (пост/рилс/карусель/видео/шортс и т.д., набор зависит от
   платформы).
3. **Сравнение аккаунтов** — таблица метрик бок о бок + наложенные
   графики трендов (подписчики, ER и т.д.) за выбранный период, для
   2–5 аккаунтов одновременно, в т.ч. с разных платформ.

## 4. Модель данных (PostgreSQL)

**`accounts`** — отслеживаемая страница
`id, platform (instagram/vk/youtube/telegram/linkedin), external_id, name, avatar_url, type (own/client/public_no_access), is_active, created_at`

**`account_credentials`** — токены доступа (пусто для аккаунтов без
выданного доступа)
`account_id, encrypted_token, token_expires_at, refresh_token`

**`account_snapshots`** — ежедневный срез метрик аккаунта; основа для
графиков трендов и сравнения
`account_id, date, followers_count, following_count, posts_count, avg_reach, avg_er`

**`posts`** — посты аккаунта, апсерт по `external_post_id` при каждом
sync
`id, account_id, external_post_id, type (post/reel/carousel/video/short/story...), published_at, permalink, thumbnail_url, caption, likes, comments, shares, views, reach, er (computed), last_synced_at`

**`sync_jobs`** — история запусков сбора
`id, account_id, trigger (scheduled/manual), status (pending/running/success/failed), error_message, started_at, finished_at`

**`users`** — сотрудники агентства
`id, email, password_hash, name, created_at`

### Решения по данным
- Тренды и сравнение строятся на `account_snapshots` по датам, не
  пересчитываются на лету из постов.
- ER считается по каждому посту: `(likes + comments + shares) / followers`
  на момент публикации; агрегируется в `account_snapshots.avg_er` за
  день.
- Типы постов приводятся коннектором к общему enum-набору; не все
  платформы используют все значения.

## 5. Пайплайн сбора данных

**Плановый сбор (ежедневно):**
1. Scheduler ставит job для каждого активного аккаунта.
2. Воркер вызывает коннектор → `getAccountStats()` + `getPosts(period)`.
3. Коннектор нормализует ответ → апсерт в `posts`, новая строка в
   `account_snapshots` за сегодня.
4. Результат пишется в `sync_jobs`.

**Ручное обновление:**
- Кнопка на странице аккаунта → создаётся `sync_job(trigger=manual)` с
  приоритетом выше плановых → фронт поллит статус
  (`pending → running → success/failed`).
- Через очередь, а не синхронно — чтобы не блокировать HTTP-запрос при
  пагинации и не слать параллельные запросы с одним токеном.

**Rate limits:** job'ы одной платформы обрабатываются последовательно
с паузой, учитывающей лимиты конкретной платформы (настройка на
уровне коннектора).

**Чтение фронтендом:** все страницы дашборда читают из
`accounts`/`account_snapshots`/`posts` — без обращения к внешним API в
момент открытия страницы, для быстрого и предсказуемого отклика.

## 6. Обработка ошибок

- **Истёкший токен** → job `failed` с причиной `token_expired`; в UI
  на карточке аккаунта — бейдж "нужно переавторизовать" со ссылкой на
  переподключение через OAuth.
- **Rate limit платформы** → retry с backoff, не блокирует остальные
  job'ы в очереди.
- **Аккаунт стал приватным/удалён** → job `failed` с понятной
  причиной; после N неудачных попыток подряд `is_active=false`,
  агентство уведомляется в UI.
- **Частичный успех** (например, метрики получены, часть постов —
  нет) → сохраняется то, что получено; в логе job'а фиксируется, какие
  посты не удалось обновить; полного отката нет.

## 7. Авторизация

- Сотрудники логинятся по email/паролю, единая роль без разделения
  прав.
- JWT-сессия на фронтенде.
- Токены соцсетей (`account_credentials`) хранятся зашифрованными
  (AES) в БД; ключ шифрования — из переменной окружения/секрет-
  менеджера, не в коде.

## 8. Тестирование

- **Коннекторы** — unit-тесты нормализации ответов платформы в общий
  формат, на фикстурах реальных JSON-ответов каждой платформы
  (наиболее рискованная часть — форматы платформ меняются).
- **Расчёт ER и агрегатов** — unit-тесты формул, включая edge-cases (0
  подписчиков, аккаунт без постов за период).
- **API-слой** — интеграционные тесты эндпоинтов обзора, детальной
  статистики, сравнения, ручного refresh — на тестовой БД.
- **Очередь/scheduler** — тест retry-backoff и отсутствия
  параллельных запросов с одним токеном.
- **Frontend** — тесты компонентов (таблица сравнения, фильтр по типу
  поста, графики трендов) на замоканных данных; e2e (Playwright) на
  сценарий: выбрать аккаунты → сравнение → детальная страница →
  фильтр постов по типу.

## 9. Вне рамок MVP

- Скрапинг чужих аккаунтов без официального доступа — исключён по
  юридическим и техническим причинам (см. раздел 1).
- Клиентский доступ к дашборду (роли/права) — не нужен, только
  сотрудники агентства.
- Real-time/почасовое обновление — не нужно, дневного цикла +
  ручного обновления достаточно.
